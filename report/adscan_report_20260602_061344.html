AD-005krbtgt Password Never Changed — Golden Ticket Risk
🔴 CRITICALKerberos▼
📋 Description

The krbtgt password has NEVER been changed.
Attacker with this hash can forge Golden Tickets for permanent domain access.

⚡ Exploitable By
⚡ Domain Admin
📍 Found In

LDAP → pwdLastSet attribute on krbtgt account (value: 0 / null)

🎯 Affected (1)
  • krbtgt
🛠 Remediation

Reset krbtgt password TWICE (10 hours apart).
Use Microsoft Reset-KrbtgtPassword script. Rotate every 180 days.

AD-001AS-REP Roasting — Pre-authentication Disabled
🟠 HIGHKerberos▼
📋 Description

1 account(s) have Kerberos pre-authentication disabled.
Attacker can request AS-REP ticket without credentials and crack offline.

⚡ Exploitable By
⚡ Low-privileged domain user
📍 Found In

LDAP → userAccountControl (flag: DONT_REQ_PREAUTH = 0x400000)

🎯 Affected (1)
  • test.user
🛠 Remediation

Set-ADAccountControl -Identity -DoesNotRequirePreAuth $false
ADUC → Account tab → uncheck 'Do not require Kerberos preauthentication'

AD-001 AS-REP Roasting
🟠 HIGH Kerberos T1558.004 ↗
⚡ Exploitable By
⚡ Low-privileged domain user
📋 What is this vulnerability?

When a user account has Kerberos pre-authentication disabled (UAC flag 0x400000), any attacker on the network can request an AS-REP response from the Domain Controller for that account without providing any credentials. The response contains a portion encrypted with the user's password hash, which can then be cracked offline using tools like Hashcat or John the Ripper — no foothold required.

🛠 How to fix it

1. Enable Kerberos pre-authentication for all user accounts: Set-ADUser -Identity <user> -KerberosEncryptionType AES256
2. Run the following to find all vulnerable accounts: Get-ADUser -Filter {DoesNotRequirePreAuth -eq $true}
3. Only disable pre-auth if absolutely required by a legacy application — document the exception.
4. Enable auditing on AS-REP requests (Event ID 4768).

🔍 Detection Source

LDAP → userAccountControl (0x400000)

AD-002 Kerberoasting — SPN Accounts
🟠 HIGH Kerberos T1558.003 ↗
⚡ Exploitable By
⚡ Low-privileged domain user
📋 What is this vulnerability?

Any domain user can request a Kerberos service ticket (TGS) for any account with a registered Service Principal Name (SPN). The ticket is encrypted with the account's NTLM password hash. An attacker can capture this ticket and crack it offline — especially dangerous when service accounts use RC4 encryption instead of AES256, as RC4 hashes crack significantly faster.

🛠 How to fix it

1. Audit SPNs: Get-ADUser -Filter {ServicePrincipalName -ne '$null'} -Properties ServicePrincipalName
2. Migrate service accounts to Group Managed Service Accounts (gMSA) — their passwords rotate automatically and are 120 characters long.
3. Enforce AES256 encryption: Set-ADUser -Identity <svc> -KerberosEncryptionType AES256
4. Ensure service account passwords are at least 25 characters and rotated regularly.

🔍 Detection Source

LDAP → servicePrincipalName

AD-003 Unconstrained Kerberos Delegation
🔴 CRITICAL Kerberos T1134.001 ↗
⚡ Exploitable By
⚡ Local administrator
📋 What is this vulnerability?

When a computer or user account has Unconstrained Delegation enabled, any user who authenticates to a service on that machine will have their TGT (Ticket Granting Ticket) forwarded to and cached on that machine. An attacker who compromises the machine can harvest these cached TGTs and impersonate any user — including Domain Admins — who has recently authenticated.

🛠 How to fix it

1. Find all accounts with unconstrained delegation: Get-ADComputer -Filter {TrustedForDelegation -eq $true}
2. Remove the flag unless strictly required: Set-ADComputer -Identity <PC> -TrustedForDelegation $false
3. Add sensitive accounts (Domain Admins, service accounts) to the Protected Users security group — this group prevents credential caching.
4. If delegation is needed, use Constrained Delegation (msDS-AllowedToDelegateTo) instead.

LDAP → userAccountControl (0x080000)

⚡ Exploitable By
⚡ Local administrator
📋 What is this vulnerability?

Computer objects with no OS version information in Active Directory indicate systems that have not properly registered their details, are offline for extended periods, or are unmanaged/rogue machines. These systems cannot be assessed for patch status, creating a blind spot in security monitoring.

🛠 How to fix it

1. Identify unresponsive systems: Get-ADComputer -Filter {OperatingSystemVersion -notlike '*'}.
2. Verify whether these are still active systems using network scanning.
3. Disable AD objects for systems that are confirmed decommissioned.
4. Ensure WSUS or SCCM/Intune is deployed to all systems for centralized patch visibility.

🔍 Detection Source

LDAP → computer → operatingSystemVersion (empty)

AD-035 WinRM Enabled on Domain Controller
🟡 MEDIUM System Security T1021.006 ↗
⚡ Exploitable By
⚡ Low-privileged domain user
📋 What is this vulnerability?

WinRM (Windows Remote Management) on ports 5985/5986 enables remote PowerShell execution. If WinRM is enabled on a Domain Controller, any account with sufficient permissions can execute commands remotely on the most sensitive server in the domain. WinRM is also used by tools like Empire and CrackMapExec for lateral movement.

🛠 How to fix it

1. Disable WinRM on Domain Controllers unless actively required for management: Disable-PSRemoting -Force.
2. If WinRM is needed, restrict to management IP addresses via Windows Firewall: New-NetFirewallRule -Name 'WinRM-Admin' -LocalPort 5985 -RemoteAddress 10.0.0.0/24.
3. Use Jump Servers / PAWs (Privileged Access Workstations) for all DC management.

🔍 Detection Source

nmap → port 5985/5986 on DC IP

AD-036 SMBv1 Risk on Legacy Systems
🟠 HIGH System Security T1210 ↗
⚡ Exploitable By
⚡ External attacker (no creds)
📋 What is this vulnerability?

SMBv1 is a 30-year-old protocol with critical, unpatched vulnerabilities including EternalBlue (CVE-2017-0144). EternalBlue was used in the WannaCry and NotPetya ransomware attacks that caused billions of dollars in damages. Any system running SMBv1 is potentially vulnerable to remote code execution with no authentication required.

🛠 How to fix it

1. Disable SMBv1 on all Windows systems via PowerShell: Set-SmbServerConfiguration -EnableSMB1Protocol $false.
2. Use Group Policy to prevent re-enabling: Computer Configuration → Administrative Templates → Network → Lanman Server → Enable insecure guest logons.
3. Block TCP port 445 inbound from the internet at your perimeter firewall.
4. Monitor for SMBv1 connections using Event ID 3000 in the SMB Client Operational log.

🔍 Detection Source

nmap → port 445 + LDAP → EOL computers

AD-037 Anonymous LDAP Bind Possible
🟠 HIGH System Security T1087.002 ↗
⚡ Exploitable By
⚡ Anonymous / unauthenticated
📋 What is this vulnerability?

Anonymous LDAP bind allows an unauthenticated attacker (or someone with no domain account) to connect to the LDAP service on the DC and potentially query directory information. Even if queries return limited data, the ability to bind anonymously is a prerequisite for further unauthenticated enumeration.

🛠 How to fix it

1. Disable anonymous LDAP bind via Group Policy: Computer Configuration → Windows Settings → Security Settings → Local Policies → Security Options → Network access: Allow anonymous SID/Name translation → Disabled.
2. Set 'dsHeuristics' to disable anonymous access: modify attribute on the CN=Directory Service,CN=Windows NT,CN=Services,CN=Configuration object.
3. Verify with: ldapsearch -H ldap://DC_IP -x -b '' -s base '(objectClass=*)' 2>&1.

🔍 Detection Source

LDAP → anonymous bind attempt

AD-038 Excessive Number of GPOs (>20)
🟢 LOW Group Policy T1484.001 ↗
⚡ Exploitable By
⚡ Domain Admin
📋 What is this vulnerability?

Having more than 20 Group Policy Objects indicates GPO sprawl — accumulated configurations from years of changes, often without cleanup. Excessive GPOs make it difficult to audit security settings, increase processing time at login, and can contain conflicting or outdated security configurations that create gaps.

🛠 How to fix it

1. Audit all GPOs: Get-GPO -All | Select DisplayName, GpoStatus, CreationTime.
2. Identify and delete empty, disabled, or unlinked GPOs.
3. Consolidate overlapping GPOs where possible.
4. Document the purpose of every GPO in its description field.
5. Use GPO modeling (GPMC) to verify effective settings after consolidation.

🔍 Detection Source

LDAP → groupPolicyContainer count

AD-039 Empty / Unused GPOs
🟢 LOW Group Policy T1484.001 ↗
⚡ Exploitable By
⚡ Domain Admin
📋 What is this vulnerability?

GPOs that are not linked to any Organizational Unit, site, or domain are unused and waste processing time. More critically, empty GPOs (with no settings configured) may indicate a failed GPO deletion attempt, leaving orphaned objects that clutter AD and confuse administrators.

🛠 How to fix it

1. Find unlinked GPOs: Get-GPO -All | Where {$_ | Get-GPOReport -ReportType XML | Select-String -NotMatch 'LinksTo'}.
2. Review each unlinked GPO — verify it is genuinely unused.
3. Delete confirmed unused GPOs after a 30-day review period.
4. Implement a GPO naming convention (e.g., CORP-SEC-PasswordPolicy-v1) for better management.

🔍 Detection Source

LDAP → groupPolicyContainer → no linked OUs

AD-040 Bidirectional Domain Trusts
🟡 MEDIUM Domain Config T1482 ↗
⚡ Exploitable By
⚡ Domain Admin
📋 What is this vulnerability?

A bidirectional (two-way) domain trust means that users in both domains can authenticate to resources in either domain. If one domain is compromised, the attacker can potentially pivot into the trusted domain. Bidirectional trusts are particularly dangerous when one of the domains has weaker security posture.

🛠 How to fix it

1. Audit trusts: Get-ADTrust -Filter *.
2. Convert bidirectional trusts to one-way (selective trust) where possible.
3. Enable SID Filtering on all external trusts to prevent privilege escalation across trust boundaries: netdom trust TrustingDomain /domain:TrustedDomain /enablesidhistory:no.
4. Enable Selective Authentication to limit which resources trusted users can access.

🔍 Detection Source

LDAP → trustedDomain → trustDirection = 3

AD-041 Domain Functional Level Below 2016
🟡 MEDIUM Domain Config T1562 ↗
⚡ Exploitable By
⚡ Domain Admin
📋 What is this vulnerability?

A domain functional level below Windows Server 2016 means the domain cannot take advantage of modern security features including Protected Users enhancements, compound authentication, Kerberos FAST (armoring), and privileged access management features. Lower functional levels also support legacy authentication protocols with known weaknesses.

🛠 How to fix it

1. Check current level: Get-ADDomain | Select DomainMode.
2. Upgrade to Windows Server 2016 or 2019 functional level after ensuring all DCs are running at least Windows Server 2016.
3. Test impact on any legacy applications that rely on older protocols.
4. Raising the functional level enables security improvements like Kerberos armoring (FAST) and reduced-privilege tickets.

LDAP → domainDNS → msDS-Behavior-Version

AD-042 AD Recycle Bin Not Enabled
🟢 LOW Domain Config T1485 ↗
⚡ Exploitable By
⚡ Domain Admin
📋 What is this vulnerability?

Without the AD Recycle Bin, deleted Active Directory objects (users, computers, groups) are permanently destroyed after a short tombstone period. This makes recovery from accidental deletions, ransomware attacks, or malicious deletions significantly more complex and potentially impossible — requiring a full domain restore from backup.

🛠 How to fix it

1. Enable the AD Recycle Bin via Active Directory Administrative Center: Enable Recycle Bin.
2. Or via PowerShell: Enable-ADOptionalFeature 'Recycle Bin Feature' -Scope ForestOrConfigurationSet -Target (Get-ADForest).RootDomain.
3. Note: This is a one-way operation and requires Forest functional level 2008 R2 or higher.
4. Set the deleted object lifetime to at least 180 days.

🔍 Detection Source

LDAP → Optional Features → Recycle Bin

AD-043 Protected Users Group Empty
🟡 MEDIUM Domain Config T1558 ↗
⚡ Exploitable By
⚡ Domain Admin
📋 What is this vulnerability?

The Protected Users security group provides additional credential protection for privileged accounts — preventing credential caching, prohibiting NTLM authentication, preventing DES/RC4 Kerberos, and requiring AES Kerberos. An empty Protected Users group means no accounts benefit from these enhanced protections, leaving all users vulnerable to credential theft attacks like Pass-the-Hash and Pass-the-Ticket.

🛠 How to fix it

1. Add all Domain Admins, Enterprise Admins, and Schema Admins to Protected Users.
2. Test impact first — Protected Users breaks NTLM authentication, which may affect some legacy applications.
3. Add: Add-ADGroupMember 'Protected Users' -Members (Get-ADGroupMember 'Domain Admins').
4. Document any accounts that cannot be added due to NTLM dependencies.

🔍 Detection Source

LDAP → Protected Users group → member count = 0

Anonymous LDAP enumeration allows any unauthenticated user on the network to query the Active Directory base DN and retrieve information about users, groups, computers, and domain structure. 🛠 How to fix it

AD-045 Shadow Admin Accounts Detected
🟡 MEDIUM Privileged Accounts T1078.002 ↗
⚡ Exploitable By
⚡ Low-privileged domain user
📋 What is this vulnerability?

The adminCount=1 attribute is set automatically on accounts that are or were members of privileged groups, removing them from inheritance of permissions from parent OUs. 'Shadow admin' accounts are those with adminCount=1 that are no longer in any privileged group — suggesting they were historically privileged and may still have residual permissions that were never cleaned up.

🛠 How to fix it

1. Find shadow admins: Get-ADUser -Filter {AdminCount -eq 1} -Properties AdminCount,MemberOf | Where {$_.MemberOf -notmatch 'Admin'}.
2. Review each account — if not intentionally privileged, reset AdminCount: Set-ADUser -Identity <user> -Replace @{adminCount=0}.
3. Re-enable inheritance of permissions on the account's ACL.
4. Investigate how the account acquired adminCount=1.

🔍 Detection Source

LDAP → adminCount=1 attribute cross-check

AD-046 Reversible Encryption Enabled
🟠 HIGH Account Hygiene T1003 ↗
⚡ Exploitable By
⚡ Low-privileged domain user
📋 What is this vulnerability?

The 'Store password using reversible encryption' setting causes Active Directory to store passwords in a form that can be decrypted back to plaintext — essentially equivalent to storing passwords in clear text. Any administrator with access to the AD database (NTDS.dit) or a DCSync capability can recover the plaintext passwords of all affected accounts.

🛠 How to fix it

1. Disable reversible encryption in Group Policy: Computer Configuration → Windows Settings → Security Settings → Account Policies → Password Policy → Store passwords using reversible encryption → Disabled.
2. Find affected accounts: Get-ADUser -Filter {AllowReversiblePasswordEncryption -eq $true}.
3. Force password reset for all affected users — the old reversible hash remains until the password changes.

🔍 Detection Source

LDAP → UAC (ADS_UF_ENCRYPTED_TEXT_PASSWORD)

AD-047 DC Running End-of-Life OS
🔴 CRITICAL System Security T1190 ↗
⚡ Exploitable By
⚡ External attacker (no creds)
📋 What is this vulnerability?

A Domain Controller running an end-of-life operating system is the most critical finding possible. DCs are the most sensitive servers in the domain — they hold all credentials, policies, and trust relationships. An EOL DC has unpatched, publicly documented vulnerabilities that can lead to complete domain compromise with no authentication required in some cases (e.g., ZeroLogon, PrintNightmare).

🛠 How to fix it

1. This is an emergency — treat as a critical incident.
2. Immediately isolate the EOL DC from untrusted network segments.
3. Deploy a new DC running Windows Server 2022 and transfer all FSMO roles to it.
4. Demote and decommission the EOL DC as a top priority.
5. Apply compensating controls immediately: host firewall, disable unnecessary services, monitor 24/7.

🔍 Detection Source

LDAP → DC computer objects → operatingSystem

AD-048 DC Not Owned by Domain Admins
🟠 HIGH Domain Config T1222 ↗
⚡ Exploitable By
⚡ Domain Admin
📋 What is this vulnerability?

Domain Controller computer objects should be owned by the Domain Admins group. If the owner is a regular user account or a service account, that account may have the ability to modify the DC object's security descriptor — potentially granting itself or others elevated permissions on the most sensitive servers in the domain.

🛠 How to fix it

1. Check DC object ownership: Get-ADComputer <DC_Name> -Properties nTSecurityDescriptor | Select -ExpandProperty nTSecurityDescriptor | Select Owner.
2. Reset ownership to Domain Admins using ADSI Edit or: $acl = Get-Acl 'AD:<DC_DN>'; $acl.SetOwner([System.Security.Principal.NTAccount]'DOMAIN\Domain Admins'); Set-Acl -Path 'AD:<DC_DN>' -AclObject $acl.
3. Regularly audit DC object ACLs.

🔍 Detection Source

LDAP → DC objects → nTSecurityDescriptor

AD-049 High Password Spray Attack Risk
🟠 HIGH Password Policy T1110.003 ↗
⚡ Exploitable By
⚡ External attacker (no creds)
📋 What is this vulnerability?

Password spray is an attack where a single common password (e.g., 'Summer2024!') is tried against every account in the domain. When the lockout threshold is 0 (no lockout) AND minimum password length is less than 8, the domain is highly vulnerable — an attacker can spray hundreds of accounts with common passwords indefinitely without any lockout, and short passwords are more likely to match common patterns.

🛠 How to fix it

1. Immediately set account lockout threshold to 5 in Group Policy.
2. Set minimum password length to at least 12 characters.
3. Deploy Microsoft Entra ID Password Protection to block common passwords and domain-specific terms.
4. Enable Microsoft Defender for Identity or a SIEM rule to detect spray patterns (many failed logins from one source to many accounts within a short time window).

🔍 Detection Source

LDAP → lockoutThreshold=0 + minPwdLength<8

AD-050 Nested Groups in Privileged Groups
🟡 MEDIUM Privileged Accounts T1078.002 ↗
⚡ Exploitable By
⚡ Low-privileged domain user
📋 What is this vulnerability?

When group objects (rather than user objects) are nested inside privileged groups like Domain Admins, it becomes very difficult to enumerate who actually has domain admin privileges. An attacker who compromises any account in a deeply nested group chain may unexpectedly have Domain Admin rights. This is a common misconfiguration that enables privilege escalation and makes access reviews nearly impossible.

🛠 How to fix it

1. Audit nesting: Get-ADGroupMember 'Domain Admins' -Recursive | Where {$_.objectClass -eq 'group'}.
2. Remove group objects from Domain Admins — only individual user accounts should be direct members.
3. Document and flatten all nested privileged group structures.
4. Use BloodHound to visualize all effective membership chains and identify unexpected privilege paths.

🔍 Detection Source

LDAP → privileged groups → group objects nested
